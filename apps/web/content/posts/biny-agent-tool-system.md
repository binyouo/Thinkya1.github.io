在写一个玩具级别的 Agent 时，工具调用通常极其简单：写个函数、声明参数 Schema、交给模型，收到返回值直接执行。

但在开发 [Biny Agent](https://github.com/binyouo/Biny-Agent) 的过程中，随着接入的 MCP Server、本地插件、工作区 Skill 与内置工具不断增加，工具系统的核心矛盾迅速发生转移：
- 注册了上百个工具，如果每一轮都把完整定义塞给主模型，输入成本高昂且严重稀释注意力；
- 如果只留几个基础工具，模型在多步执行中遇到能力缺失，如何做到准确感知并动态补全？
- 来源各异的调用（内置文件读写、MCP 进程、沙箱命令、JS 脚本），如何由统一的权限策略与资源锁进行约束？
- 涉及写文件时，如果外部编辑器并发修改了内容，怎样避免静默覆盖？
- 远端网络调用中途断线，客户端收到错误时，底层究竟是“未执行”还是“已执行但回执丢失”？

做 Biny 的工具系统，我最关心的不是“支持了多少个花哨的工具”，而是**一个工具从被发现到真正产生外部副作用，中间的每一步状态能不能说清楚、控得住**。

这篇文章沿着这条完整的执行生命周期，聊聊我在 Biny 中的架构设计与工程权衡。

## 1. 工具统一注册，定义按需加载

我首先在架构上确立了两个严格解耦的集合：**系统拥有的工具全集**，以及**模型当前轮次可见的工具子集**。

在 Biny 内部，内置工具（文件、搜索、Git、命令）以及 MCP、Plugin、Skill、Subagent 暴露的能力，统一由 `ToolRegistry` 接管。注册表维护着工具名称、详细描述、Zod 参数 Schema、来源命名空间以及资源访问特征。

```text
┌────────────────────────────────────────────────────────┐
│                      ToolRegistry                      │
│ 完整工具目录（内置工具 + MCP + Plugin + Skill 入口）    │
└───────────────────────────┬────────────────────────────┘
                            │ 按任务动态过滤与按需加载
                            ▼
┌────────────────────────────────────────────────────────┐
│                   当前模型上下文可见工具               │
│ 常驻基础能力 (Read, Write, Edit, Bash) + 本轮动态预选能力 │
└────────────────────────────────────────────────────────┘
```

假设用户接入了 3 个 MCP Server，共带来 80 多个外部工具。如果当前任务仅仅是“修复 package.json 中的拼写错误”，把 GitHub PR、数据库查询、日历同步等工具的完整 Schema 全部灌入模型上下文，不仅白白消耗数千 Token，还会显著增加模型误选工具的概率。

因此我的策略是：**工具目录保持全量能力，模型输入只开放当前所需**。

在自动模式下，系统仅将 `Read`、`Write`、`Edit`、`Bash` 等核心编码能力，以及工具发现（`ToolSearch`）和长结果回读（`read_tool_result`）作为常驻工具；其余具体工具按任务按需披露。仅这项收缩，就将基础常驻工具的静态字符数从 11,605 降至 5,668，大幅净化了初始上下文。

## 2. 先辅助预选，缺少能力时再语义检索

如果初始只暴露常驻基础工具，主模型在执行复杂多步任务时（例如突然需要调用 GitHub API 查看 Issue），手里没有相关工具，任务就会卡死。

针对工具发现，Biny 采用了**回合前辅助预选 + 运行中 ToolSearch 按需发现**的双层设计。

### 回合前：辅助模型预选

在主模型请求发出之前，`capabilityPreselection` 会将当前用户指令及近期对话摘要，连同候选工具的“名称 + 简要一句话描述”，交给轻量级辅助模型进行快速预选。

这里有几个关键工程约束：
- **只给名片，不给完整 Schema**：预选阶段只传递名称与概括，辅助模型返回候选名称列表；
- **本地注册表强校验**：辅助模型选出的名称必须经由本地 `ToolRegistry` 二次核验，凭空幻觉出来的工具名会被直接剔除；
- **动态预算限制**：我设置了单轮新选工具的配额上限，防止辅助模型一次性引入过多边角工具；
- **确定性绕过**：如果用户在提示词中明确点名了某个已注册的工具名，本地直接放行进入候选集，无需让模型猜测。

我曾在 8 个复杂多工具测试任务中做过对照实验：
- **方案 A（每回合辅助预选）**：8 个任务全部顺利完成，首请求中位延迟 2.28 秒，总消耗 95,982 Token；
- **方案 B（仅留基础工具，缺了靠 ToolSearch 搜索）**：仅完成 4 个任务，首请求中位延迟仅 0.106 秒，总消耗 65,312 Token。

未完成的那一半任务，往往是因为主模型在多步推理中注意力被分散，“根本没有意识到要去搜索工具”。尽管预选带来了额外的一次轻量模型调用，但它换来了成倍提升的任务完备率。

### 运行中：ToolSearch 语义补漏

预选是回合开始前的静态预测，但随着任务推进，模型发现了深层依赖，仍需补充新能力。此时模型可以主动调用 `ToolSearch`。

`ToolSearch` 区分两种匹配路径：
1. **精确名查找**：若查询中包含完整注册工具名，直接在本地秒级命中；
2. **意图语义选择**：若用户以自然语言表达意图（如“怎么查看 PR 评审意见”），则将合格工具的说明交给辅助模型进行语义打分与选择。

命中并校验后的工具，其完整 Schema 会被立即注入到下一步的模型请求中。

## 3. MCP 连接、工具发现与实际调用三态解耦

在接入 MCP（Model Context Protocol）协议时，很多初期设计容易把“连接建立”、“工具发现”与“实际调用”搅在一起，导致单个慢服务的网络抖动拖垮整个 Agent。

Biny 在架构上将这三者明确拆解为独立状态机：

| 阶段 | 核心职责 | 检查边界与异常隔离 |
| --- | --- | --- |
| **连接（Connect）** | 建立 stdio / HTTP 通信信道 | 设置异步等待预算，慢服务在后台连接，不阻塞 Agent 主循环 |
| **发现（Discover）** | 解析工具目录与 Schema | 同一 Runtime Host 内短期缓存目录，Schema 更新时按版本失效 |
| **执行（Execute）** | 真正产生外部副作用 | 严格检查权限、目标、调用结果与取消排空 |

在 Runtime 启动时，Biny 异步连接启用的 MCP Server，并设置就绪等待预算。已缓存的工具目录可在服务短暂重连时先行用于工具发现，但**实际执行必须等到连接就绪**。单个 MCP Server 崩溃或断开，其异常被严格限制在自身的命名空间内，不会引发整个运行时雪崩。

## 4. 统一执行协调器（ToolExecutionCoordinator）

工具发现只是第一步；当模型发出工具调用指令后，调用形式可以五花八门（直接单工具调用、多工具并发调用、或是通过 Code Mode 在 QuickJS 解释器中运行一段 JS 编排脚本），但**产生副作用的执行入口必须彻底收口**。

Biny 通过 `ToolExecutionCoordinator` 协调所有工具调用，整条执行管道严格走过七个阶段：

```text
[发起工具调用请求]
        │
        ▼
[1. 参数校验]     ──► Zod Schema 强类型约束，非法入参直接拦截
        │
        ▼
[2. 上下文准备]   ──► 解析绝对路径、执行域与资源边界
        │
        ▼
[3. 权限与守卫]   ──► 四级权限模式判定；高危操作触发 criticalAlwaysAsk（强制输入 yes）
        │
        ▼
[4. 资源调度锁]   ──► 评估资源并发冲突，顺序排队或受控并发
        │
        ▼
[5. 目标快照复核] ──► 检查待操作文件/实体的当前版本，防并发篡改
        │
        ▼
[6. 执行与状态机] ──► 派发底层实现，捕获超时，记录执行状态
        │
        ▼
[7. 结果处理归档] ──► 脱敏敏感信息，超长日志转存，生成 ToolResultMessage
```

### 严格的四级权限防线

系统全局配置支持四种权限模式：
- `read-only`：严禁一切非读取操作；
- `ask`：除显式白名单与只读操作外，其余调用全部弹窗询问；
- `auto`：自动放行安全操作，高危行为依然询问；
- `full-access`：跳过普通交互审批，但依然受到 `denyPaths`（如禁止触碰 `.env`、`~/.ssh/`）的绝对拦截。

对于破坏性操作（如删除核心文件或执行危险 Shell 命令），`criticalAlwaysAsk` 机制要求用户必须**完整输入 `yes`**，彻底杜绝了因误按 Enter 或单键回车而意外执行灾难性操作的风险。

### 受限 Code Mode（QuickJS 沙箱）

在需要同时读取分析多个文件的场景下，Biny 支持可选的 Code Mode。模型可以输出一段 JavaScript 脚本，在嵌入的 **QuickJS 隔离沙箱** 中运行。

脚本内部只能访问经过宿主严格登记的只读能力（读文件、按名查找、内容 Grep、历史记忆召回）；脚本**没有任何原生网络、文件系统直接调用或子进程生成权限**。脚本内部调用的每一次读操作，底层依然回流到 `ToolExecutionCoordinator` 走完全部权限与配额核查。

![不同来源的工具调用经过统一执行协调器，依次处理参数、目标、权限、调度、执行与记录](/images/biny-tool-system/execution-coordinator.svg)

## 5. 文件编辑：协议灵活，底层事务与快照强一致

代码编辑是 Coding Agent 最核心、也最容易出错的环节。

Biny 适配了多种模型编辑协议，但在底层写入时，统一收敛在强一致性事务之下：

### 三种编辑定位方式

1. **字符串替换（String Replace）**：模型提供 `old_string` 与 `new_string`。优先精准匹配；当全文出现多处相同片段时，若未显式声明 `replace_all`，系统会主动报错并要求模型补充上下文，**宁可定位失败，绝不静默挑第一个位置错改**。
2. **Hashline 行号摘要锚点**：读取文件时每行附带行号与内容 Hash（例如 `12#A1B2C3D4`），编辑时校验锚点有效性。它能精准识别“模型基于旧视图修改，但文件行数已变动”的情况。
3. **结构化 Patch（apply_patch）**：针对天然支持 Patch 协议的高阶模型，解析标准 `@@` 上下文与增删行。

### 快照绑定与同目录原子提交

比“怎么定位修改”更危险的是“并发覆盖”：模型读了文件 A，在推理期间用户在外部 IDE 里也修改了文件 A。如果 Agent 盲目写回，用户的修改就会被静默抹杀。

Biny 的防护策略非常严密：
- **执行绑定已审批快照**：`Edit` 的执行必须绑定读取或审批时刻的文件内容 Hash 快照；
- **同目录原子写入**：写入时先在同一目录下创建 `.tmp` 临时文件并同步刷盘，避免跨分区重命名失效；
- **提交前最终版本复核**：在最终通过系统级 rename 覆盖目标前，再次读取当前磁盘文件 Hash。一旦发现磁盘内容与先前绑定的快照不一致，立即中止提交并返回版本冲突错误。

![字符串替换、Hashline 和 Patch 汇入文件校验与安全提交链路；版本变化时拒绝继续写入](/images/biny-tool-system/file-editing.svg)

## 6. 长工具结果与后台进程治理

工具返回的结果如果动辄数万行，不仅会直接撑爆当前窗口，还会让后续每一轮请求都背负沉重开销。

### 工具结果按需归档

对超出预算的大型输出，Biny 实行**本地持久归档 + 受限预览返回**：
- 完整的执行结果（如大段编译日志或全库搜索结果）落盘归档至 Session 目录；
- 模型先拿到经过安全截断的高信号预览（标记原始大小与截断位置），以及一个归档引用 ID；
- 模型若确认需要追查特定段落，再通过 `read_tool_result` 携带 offset 按需续读。

这保证了模型既能获得关键错误线索，又不必在上下文里反复拖拽海量日志。

### 后台进程的流式缓冲与 Gap 标记

执行长耗时任务时，进程通过 `ProcessStatus` 进行异步查询与字节级续读。

宿主对进程日志维持内存分段缓冲与 1 MiB 环形队列淘汰机制：
- 慢速写盘时优先丢弃较早的暂存数据，绝不因日志过多而强行杀掉运行中的后台命令；
- 当读取游标落入已被淘汰的区间时，返回结构中会明确带上 `output.gap`，告知模型 `[startOffset, endOffset)` 范围的数据已丢失。这种透明的失败表达，远比静默截断更能让模型做出正确的工程决策。

## 7. 外部操作结果未知时：先核查，再恢复

工具调用最危险的时刻，是**网络或进程断开时把“收到错误”当成“没有执行”**。

典型场景：Agent 通过 MCP 向远端创建某个云资源，网络在等待回执时突然断开。此时远端其实已经创建成功，但客户端只抓到了网络超时。如果直接判定失败并盲目重试，就会导致灾难性的重复资源创建。

Biny 在状态流转上给出了严格设计：

```text
               ┌───────────────────────┐
               │ 派发外部调用 (如 MCP) │
               └───────────┬───────────┘
                           │ 发生断线 / 超时
                           ▼
               ┌───────────────────────┐
               │ 标记为 result: UNKNOWN│
               └───────────┬───────────┘
                           │ 拒绝盲目重放
                           ▼
               ┌───────────────────────┐
               │  结合操作 ID 与证据   │
               │  执行本地/远端幂等核查│
               └───────────────────────┘
```

1. **状态明确标记为 `UNKNOWN`**：凡是调用已离开本机但未拿到终态确认的异常，一律标记为“结果未知”，而非普通失败；
2. **取消信号与有界排空（Bounded Drain）**：
   - 内置工具严格监听 `AbortSignal`；
   - 外部调用（MCP / Plugin）采用带有确定时间上限的排空（Drain）。若超时仍未结束，当前调用会被打上**隔离（Isolated）**标记；
   - 此时 `AgentSession` 会**主动拒绝执行任何新的工具调用**，直到迟到的外部调用完全 settle，杜绝两次操作产生交叉副作用。
3. **基于操作凭据核查恢复**：重启或恢复执行时，系统依据记录的操作 ID 查验远端状态。如果远端已经存在对应对象，直接复用其成果，而不是重新派发写入。

![远端请求派发后断线，可能已经执行也可能尚未执行；客户端应记录结果未知并核查证据](/images/biny-tool-system/unknown-outcome.svg)

## 结语

在开发 Biny Agent 的工具系统时，我越来越深刻地体会到：**工具系统的技术门槛不在于能连多少个 API，而在于能否完整治理工具产生副作用的全过程**。

- **按需发现与动态预选**，让模型在庞大的工具库中保持专注与轻盈；
- **统一执行协调器与受控沙箱**，将权限、配额与审计收敛在单一出口；
- **文件快照一致性与原子事务**，保障了 Agent 与人工编辑并存时的代码安全；
- **Never Throw、结果未知状态与隔离排空**，为不可靠网络与外部系统的交互提供了底层的自愈韧性。

把这些底层的规矩立稳了，Agent 才能在真实的生产环境中做复杂且关键的工作。
