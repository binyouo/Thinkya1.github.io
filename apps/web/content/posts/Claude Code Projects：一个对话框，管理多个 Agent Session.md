在日常使用 Coding Agent 解决复杂工程问题时，开发者经常会陷入一种“人肉调度器”的窘境：

遇到大型需求，先开一个 Session 读代码理架构；有了思路后开第二个 Session 改实现；中间遇到报错，又开第三个 Session 单独调试。开发者不得不在多个终端窗口或网页标签之间反复横跳，并在每次开启新会话时机械地复制粘贴项目背景与前置结论。

Anthropic 在对 **Claude Code Projects** 的重构中，给出了一个非常具启发性的解法：**将 Project 从静态的配置文件夹（Folder）转变为持续运行的对话容器（Conversation Hub）**。

其核心在于：在底层的执行 Session 之上增加了一个项目级协调者（Coordinator），用一个统一的项目对话框承接用户的所有长期需求，将多 Session 的调度、生命周期治理与结果汇总完全收敛在系统内部。

## 一、系统架构：从树状调度到双层分工

Claude Code Projects 的核心架构可以抽象为：

```text
               ┌────────────────────────┐
               │    用户交互主入口      │
               │ (统一的 Project 对话框) │
               └───────────┬────────────┘
                           │ 持续交互
                           ▼
               ┌────────────────────────┐
               │  Project Coordinator   │◄────┐
               │  (需求拆解、调度与汇总) │     │
               └───────────┬────────────┘     │
                           │                  │ 读取/写入
          ┌────────────────┼────────────────┐ │
          ▼                ▼                ▼ │
   ┌─────────────┐  ┌─────────────┐  ┌─────────────┐
   │  Thread A   │  │  Thread B   │  │  Thread C   │
   │ (架构分析)  │  │ (核心重构)  │  │ (测试覆盖)  │
   │  分支: feat-a│  │  分支: feat-b│  │  分支: feat-c│
   └─────────────┘  └─────────────┘  └─────────────┘
          │                │                │
          └────────────────┼────────────────┘
                           ▼
               ┌────────────────────────┐
               │  Shared Project Memory │
               │ (架构共识、技术栈规范) │
               └────────────────────────┘
```

各层职责划分非常明确：

1. **Project**：项目级工作空间，绑定代码仓库、环境配置、项目规则与长期记忆；
2. **Coordinator**：顶层编排 Agent。负责理解用户输入、维护任务状态机、决定何时派发新任务或唤醒历史任务，并将各 Thread 的交付成果汇总给用户；
3. **Thread（Session）**：底层的具体执行者。每个 Thread 都是一个完整、独立的 Claude Code 会话，拥有自己的上下文与执行环境，负责具体的代码阅读、编写与测试；
4. **Shared Project Memory**：跨 Session 的持久化记忆层，记录不可动摇的技术栈决策、代码风格规范与阶段性里程碑。

### 为什么 Thread 是独立 Session 而非简单的 Subagent？

在很多 Multi-Agent 框架中，子任务通常以进程内 Subagent 的形式存在——子 Agent 的生命周期依附于父 Agent 的某一次 Turn，其上下文最终要么被父级吞吐，要么随着调用结束而彻底销毁。

而在 Projects 体系下，**每一个 Thread 都是一条持久存在的完整工作线**：
- 它具备独立的代码仓库工作区副本（Git Branch / Worktree）；
- 拥有自包含的文件修改、测试运行及工具调用生命周期；
- Coordinator 可以随时回到某个已经存在的 Thread 继续追加要求，也可以让多个 Thread 异步推进不同的子任务。

## 二、交互价值：统一的是入口，而不是执行上下文

相比“多个 Agent 跑得有多快”，这项设计最深刻的价值其实在于**交互范式的重塑**。

对于开发者而言，理想的 AI 协作界面不是一个眼花缭乱的 Agent 监控大屏，而是一个**能够持续交流的项目级对话框**：
- 今天让它重构某个性能瓶颈模块；
- 明天在同一个窗口里跟它说“继续把昨天的改动补齐边界测试”；
- 后天反馈“线上报了相关回归 Bug，快排查一下”。

用户不需要关心后台启动了多少个进程、开了多少个分支、上下文何时被截断。面对同一个 Coordinator，用户始终是在与“熟悉当前项目的资深同事”交谈。

```text
【传统交互模式】
用户 ──手动切换──► Session 1 (分析) ──复制摘要──► Session 2 (编码) ──手动同步──► Session 3 (排错)

【Projects 模式】
用户 ──单一对话框──► Coordinator ──自动派发──► [Thread 1 / Thread 2 / Thread 3 并行自治]
```

更关键的是：**系统统一的是交互入口，而不是把所有任务的执行上下文死板地堆在同一个窗口里。**

底层各个 Thread 的操作细节（翻阅几十个文件的长日志、编译重试、错误堆栈）被完全隔离在各自的会话中。用户在主界面看到的是清晰的阶段性进展和结论，只有当需要审查具体实现细节时，才按需深入特定 Thread 检查。

## 三、上下文工程：如何防止单一对话框上下文爆炸？

把长期任务收敛到同一个对话框，直觉上最让人担忧的问题就是：**随着交互时间变长，上下文窗口会不会迅速被撑爆？**

Projects 在上下文设计上至少确立了清晰的二元隔离边界：

### 1. 执行态上下文（Thread Context）

这是典型的“高消耗型上下文（Burn-down Context）”：
- 包含大量的 `Read` 输出、逐行代码 diff、编译器报错和反复试错过程；
- 这些中间细节随着任务执行呈爆炸式增长，但任务完成之后，**它们对宏观项目毫无保留价值**；
- Thread 完成后，只需向 Coordinator 返回结构化的交付摘要（修改了哪些文件、关键实现细节、验证结果与遗留风险）。Thread 内部的数万行原始执行上下文直接随会话归档，绝不回灌到 Coordinator 的主窗口中。

### 2. 编排态上下文（Coordinator Context）

Coordinator 面对的是项目的全局视图，它需要容纳：
- 用户的原始意图与后续指导；
- 当前各 Thread 的运行状态与任务依赖图；
- 各 Thread 提交的精简成果摘要。

即使过滤了底层执行细节，若一个项目持续交流数周，Coordinator 自身的历史消息依然会超限。这里结合了两种维度的治理策略：
- **动态滚动裁剪与 Compaction**：将早期已经达成闭环的任务折叠为状态快照，保留核心决策结论；
- **Project Memory 外部持久化**：将重要的架构决策与长期偏好下沉至结构化的记忆存储中，Coordinator 每轮请求按需读取，而不是把整段历史长期留在 Prompt 里。

```text
┌──────────────────────────────────────────────────────────────┐
│                    Coordinator Prompt                        │
│ ┌────────────────┐ ┌───────────────────┐ ┌─────────────────┐ │
│ │ 任务状态与依赖 │ │ 近期高层交互记录  │ │ 注入的项目记忆  │ │
│ └────────────────┘ └───────────────────┘ └─────────────────┘ │
└──────────────────────────────┬───────────────────────────────┘
                               │ 仅传递高层指令与摘要
              ┌────────────────┴────────────────┐
              ▼                                 ▼
┌───────────────────────────┐     ┌───────────────────────────┐
│     Thread A Context      │     │     Thread B Context      │
│ [文件读取 + 源码分析日志] │     │ [代码编辑 + 单元测试输出] │
│ (任务完成后独立归档隔离)   │     │ (任务完成后独立归档隔离)   │
└───────────────────────────┘     └───────────────────────────┘
```

## 四、并发与状态同步：Git 分支级别的隔离

多 Agent 协同编程不可避免地会遇到经典难题：**如果两个 Session 试图修改同一份代码，怎么办？**

在单进程或单 Agent 架构中，通常依靠文件锁或 Mutation Queue 强行串行化；而在 Projects 的多 Thread 云端架构中，这一问题被提升到了版本控制系统层面：
- 每个执行 Thread 默认在独立的 Git 分支和工作副本中运行；
- Thread 内部的修改是自洽的，测试通过后形成独立的 Commit；
- 当多个 Thread 的改动需要合入主分支时，走的是标准的 Git Pull Request / Merge 流程。

这种做法极其符合现代软件工程的最佳实践：**不要试图在内存中发明一套脆弱的并发锁，而是直接复用经过工业界几十年检验的代码分支与冲突解决机制。** 发生冲突时，Coordinator 甚至可以启动一个专门的“冲突解决 Thread”来对齐代码，或者交由人工审查裁决。

## 五、思考与启示

从软件工程视角看，Claude Code Projects 的重构给 Coding Agent 的发展指明了一个非常清晰的演进方向：

**开发者真正需要的不是去“手动操控一堆 Agent”，而是“让 Agent 具备自我拆解和管理 Session 的能力”。**

1. **入口收敛，上下文隔离**：单一的交互界面极大降低了认知负荷，而物理隔离的底层执行域保证了单次模型推理的上下文信噪比；
2. **状态分层，记忆沉淀**：区分执行过程、编排状态与长期记忆，解决了长周期任务中的信息衰减问题；
3. **基于既有工程设施管理并发**：将多 Agent 的写冲突交给 Git 分支体系消化，避免了过度设计的状态同步机制。

随着大模型执行能力的进一步提升，未来的开发范式正在从“指挥 AI 写一段函数”，真正转向“向 AI 委派一整组自组织的工程项目”。
