我把 Biny 的记忆系统设计成一套持续处理信息的流程：从交互和活动中保留有用信息，为它们保存来源与适用范围，在任务需要时取出，并随着时间修订和整理。

这套流程首先受到模型输入方式的约束。一次回答能使用的历史，必须进入这次请求的上下文；上下文容量有限，用户的经历却会持续增长。因此，保存历史和使用历史之间，需要有明确的选择过程。

第二个约束来自信息本身。任务进度变化很快，用户偏好相对稳定，项目状态会被新决定覆盖，原始活动则带着具体时间。它们未来如何被读取，决定了现在应该怎样保存。

第三个约束来自成本。回答前多一次模型调用，用户就多等一段时间；长期备忘多一段正文，后续加载它的回合就反复支付输入成本；全库相似度计算则会随记忆规模增长。这些成本发生的位置不同，需要分别安排。

**我希望这套系统能同时做到：当前任务可以继续执行，跨会话的信息可以准确复用，积累多年的记录仍然能够查找、纠正和维护。**

下面从这几个约束逐层推导，说明我为什么划分工作记忆、长期事实、文件、Crystal 和 Activity，以及提取、召回与 Sleep 怎样把它们连接起来。

## 从输入约束，推导记忆系统的职责

模型上下文里通常同时存在当前请求、最近对话、工具定义、工具结果和长期背景。记忆只是其中一部分。即使模型支持很长的输入，记忆仍然需要和当前任务竞争容量与注意力。

我首先区分两个集合：系统已经保存的信息，以及本轮实际交给模型的信息。前者可以不断积累，后者需要按任务选取。长期记忆的设计由这两个集合之间的关系展开。

### 保存要完整，读取要有选择

原始记录保留细节，便于后来核对；每轮直接读取完整历史，则会把大量与任务无关的细节一起带进来。一次调试中的重复报错、临时尝试和已放弃的方案，都可能继续占据上下文。

如果一段长度为 L 的背景在 r 个回合里固定加载，累计输入量大约就是 r × L。压缩、固定加载和按需检索会改变这部分成本的分布：压缩花费一次整理成本，固定加载持续支付阅读成本，检索则每次支付查询成本。

因此，我会先问一段信息将来怎么使用。每次都需要的少量背景适合直接读；与特定问题有关的事实适合检索；只有追查细节时才需要的原始记录，可以留在来源层。

这里的选择也影响质量。把过去所有技术决定都交给模型，模型还要自行辨认哪个项目、哪个阶段、哪个版本适用。存储层保留范围，检索层选择候选，装配层说明来源，才能减少回答阶段需要临时完成的推断。

### 提炼要减少体积，也要保留决定含义的条件

信息压缩会舍弃细节。关键在于舍弃哪些细节，是否影响未来的判断。

“用户的工作项目用 Go，个人项目用 TypeScript”可以压缩掉原对话的寒暄，却要保留两个项目的区别。写成“用户使用 Go 和 TypeScript”以后，语言名称都在，未来给个人项目选实现时需要的关系已经丢失。

我由此把语义保真放进记忆流程的每一步：提取时补齐对象和范围，去重时比较信息是否已被覆盖，合成时保留独立条件，召回时把时间和来源一起交给模型。

这也意味着，条目更短、条数更少只能说明存储形态发生了变化。要判断整理是否成功，还需要检查下一次任务能否作出相同或更合适的选择。

### 信息会改变，系统需要表达变化

用户偏好、项目依赖和近期安排都可能变化。新信息到来后，系统需要区分几种关系：对旧信息的重复、在旧信息上增加条件、描述另一段时间，以及明确纠正旧状态。

这些关系对应不同的动作。重复可以跳过，补充可以保存，历史状态可以保留时间，新状态则需要处理旧条目继续参与召回的问题。单纯追加会让矛盾累积，单纯覆盖又可能抹掉有价值的变化过程。

我的实现把这些工作分散在提取、编辑、去重和后台整理里。后面会逐一说明它们承担的范围，以及当前仍然分步执行的地方。

### 按未来的读取方式划分记忆

任务现场、稳定偏好和一天的活动具有不同的读取粒度。任务现场通常要整体恢复，偏好可以单独取用，活动则需要沿时间查看。我据此划分几种形态。

| 未来会问的问题 | 需要留下的信息 | 对应形态 |
| --- | --- | --- |
| 刚才那个错误修到哪里了？ | 目标、约束、已执行步骤、待验证事项 | 工作记忆 |
| 我平时希望技术文章怎样写？ | 能脱离原对话使用的稳定偏好 | 长期事实 |
| 开始工作前应该知道我的哪些背景？ | 经常一起阅读的画像、备忘和近期经历 | 文件记忆 |
| 这个项目过去讨论过哪些材料？ | 同一对象的名称、字段和来源关系 | Crystal |
| 上周三我在电脑上做了什么？ | 按时间组织的活动、截图和文字证据 | Activity |

![Biny 记忆系统总览：不同形态的信息分别保存，在当前回合的上下文装配处汇合](/images/biny-memory/arch-overview.png)

*保存方式由信息的用途决定；到了回答阶段，各层再汇入当前上下文。*

这个划分也决定了处理时机。回答前取出本轮需要的背景，回合结束后提取刚出现的可复用信息，定时维护处理全库积累的重复和过期。一次聊天的等待时间由前两项直接影响，全库整理则有独立的运行节奏。

这几层可以描述同一个项目，但各自保留不同的信息。工作摘要可能记录还差哪一步验证，事实条目记录稳定技术栈，Crystal 汇集相关材料，Activity 保留实际活动过程。任务需要哪种证据，就沿相应入口读取。

我把它们连接成一条信息流：原始消息和活动提供材料，摘要与事实提供便于使用的表达，文件与对象卡组织持续积累的背景，当前上下文负责消费本轮选中的信息。

## 工作记忆：压缩以后，下一步还能做对吗

用户说“继续修刚才的问题”，Agent 至少需要知道问题是什么、查过哪些位置、尝试过什么、当前卡在哪里。只留下主题，很难恢复这些状态。

原始消息最接近现场，但工具输出和中间尝试会迅速占满上下文。保存的历史越长，每轮重新阅读的成本越高。我需要在保留任务现场和控制输入规模之间，找到一个可持续的组织方式。

### 先界定任务现场包含哪些状态

我把任务现场拆成目标、约束、已知事实、已执行动作和未完成工作。目标说明最终要得到什么，约束限制允许使用的方案，已知事实支持当前判断，动作记录说明哪些路径已经走过，未完成工作决定接下来做什么。

其中最容易混淆的是判断和动作。“怀疑取消信号没有传下去”属于待验证判断，“已经给底层工具传入取消信号”属于修改动作，“底层进程已退出”则需要执行结果支持。摘要把这三者写成一句“修好了取消问题”，会让恢复后的 Agent 高估完成程度。

所以，工作记忆要保留结论所处的状态。已经定位的原因、尝试中的方案和完成的验证分别表达，下一轮就能据此选择检查、修改或继续执行。

约束尤其需要跨压缩保留。用户说过的“不要提交”“只改这个模块”“保留已有数据”，会影响后续所有动作。如果压缩只保留技术进度，却丢掉约束，任务虽然连续，行为已经偏离了用户要求。

### 用下一步要做的动作，决定摘要保留什么

压缩时，我先看哪些信息会改变后续动作：用户的目标和约束、涉及的文件与接口、已经确认的原因、做过的修改、验证结果、尚未解决的问题。

路径、函数名、命令和用户的纠正通常要具体保留。失败尝试也有价值，因为它能防止下一轮重复走回同一条路。大段重复日志可以缩短，日志里的关键错误与结论之间的关系要留下。

例如，“处理了工具超时，修改代码后测试通过”包含的恢复信息很少。我希望压缩后留下这样的工作现场：

```text
目标：工具超时后停止底层执行，避免重试造成重复操作。
定位：外层结束等待时，取消信号没有继续传给底层工具。
修改：将取消信号向下传递。
已验证：对应单元测试通过。
待验证：集成调用是否停止，重试是否会再次执行。
下一步：运行集成验证，对照取消事件与底层工具的实际状态。
```

这些句子能直接约束下一步。恢复后的 Agent 知道已经查明什么，也知道“测试通过”只覆盖了单元测试。

较早历史经过压缩，最近的原始消息继续保留。再次压缩时，把已有摘要和新增对话一起更新：已经完成的工作转成结果，刚刚出现的约束进入摘要，下一步跟随当前进度变化。

### 最近消息与压缩摘要怎样互补

最近消息保留措辞、局部引用和刚出现的细节。压缩摘要保存跨越更长历史仍然需要的状态。两者对应不同时间尺度，因此可以共同进入当前上下文。

如果把最新一轮也立即压缩，用户刚纠正的表达可能先被摘要模型重新解释；如果只保留最新消息，稍早确定的约束和原因又可能消失。保留近期原文，同时压缩较早内容，可以让当前交互保持精度，让长任务保留连续性。

摘要更新还需要处理已经失效的中间结论。前一份摘要写“怀疑网络超时”，新增对话已经证明是取消信号的问题，更新时应该把最终判断放在当前状态里，必要时将网络排查保留为已排除路径。不断追加所有旧判断，会让摘要逐渐变成另一份长历史。

我会用恢复后的动作来检查压缩效果。给定摘要与最近消息，Agent 能否找到正确文件、理解用户约束、避开已经失败的尝试，以及继续验证尚未完成的部分。这比检查摘要有没有覆盖所有话题更接近设计目标。

摘要记录的是当时对任务的理解。涉及外部副作用，还要读取相应的执行证据。例如创建工单的请求发出后进程退出，摘要里可能只有“等待回执”；恢复后要先查询远端结果，才能决定是否重试。这会直接影响任务能否安全接续。

### 为什么还需要会话摘要和项目背景

压缩摘要已经默认知道“我们正在做哪件事”。跨会话寻找历史时，首先要解决的是“应该打开哪段工作记录”。两者的入口不同。

为此，我另外生成 Thread Brief，保存会话主题、目标、涉及对象、结论，以及用户明确表示以后要做的事。它给一段长对话提供可查找的入口，后续可以继续回到原始消息。

其中，后续行动必须来自用户自己的表态，并保留原话。用户说“周末把集成测试补上”可以成为跟进事项；Agent 随口建议“以后可以补测试”，仍然是建议。这一层如果混在一起，过去的讨论就会不断长出用户从未承诺的待办。

项目背景又多跨了一层。一个项目可能有几十段会话，新任务先需要知道整体目标和当前方向，再定位相关工作线。因此，项目材料承担共同前提，Thread Brief 承担会话入口，压缩摘要承担当前任务的连续执行。

这三种信息允许使用不同的精度。项目背景保持稳定、简短；会话摘要突出这一段工作的区别；当前任务摘要保存足够具体的操作现场。

这里还有一个读取顺序的考虑。用户只给出项目名称时，项目背景可以帮助建立方向；需要定位之前讨论过的决定时，会话摘要提供候选入口；找到那段工作以后，再读取原消息与任务细节。

这种逐步展开让每一步都有明确目的。无需一开始就把几十段会话全部放进上下文，也能在确实需要细节时继续深入。摘要因此既是一种压缩结果，也是一种定位历史的索引。

## 长期事实：先决定什么值得带到下一次

“这次按钮用蓝色”和“我所有项目都优先使用深色主题”，都可能出现在一次设计讨论里。它们未来适用的范围差别很大。

把一次性要求提取成长期偏好，错误会在后续会话里反复出现。漏掉一条偏好，用户可能需要再解释一次；错误推广一条偏好，则会持续影响许多任务。这个代价差异让我把提取做得比较克制。

### 提取的单位是一条可以独立使用的信息

回合结束后，提取流程读取最近的对话片段。提示允许返回 `NO_MEMORY`，一轮通常期望得到 0～2 条。这个数量约束用来抑制“既然分析了，就必须总结点什么”的倾向。

优先进入事实库的内容包括稳定背景、长期目标、工作习惯、沟通偏好和有持续价值的项目。当前报错、一次性操作和 Agent 自己做过的动作，已经有会话或活动记录承接。

我判断提取粒度时，会把句子从对话里单独拿出来读。如果它还依赖“这个”“刚才那种”“照上面的方式”，就需要补齐对象和范围。

例如：

```text
原话：以后给我写技术博客，直接展开原理和设计取舍，少写模板化开头。

事实：用户的技术博客偏好直接展开原理与设计取舍，减少模板化开头。
```

这里保留了“技术博客”。这能让写邮件、写代码注释等其他任务继续按各自要求处理。事实越容易脱离原对话被反复使用，它的适用条件就越值得明确写出来。

### 一条事实要拆到什么程度

提取粒度太大，一条记忆可能同时包含偏好、项目状态和一次计划。之后只想修订其中一个部分，系统仍然需要重新处理整段内容。粒度太小，又会让同一个意思分散成许多条目，增加检索和整理成本。

我倾向于围绕能够独立成立、独立变化的信息划分。写作偏好与项目技术栈通常分开；同一项目当前使用的语言和包管理器可以放在一句里，因为它们经常共同参与项目背景判断。

范围本身属于事实的一部分。“默认简洁”需要知道适用于什么内容，“仅在测试环境关闭认证”需要保留环境，“迁移完成后再删除旧表”需要保留前提与顺序。提取时删掉这些短语，会让句子更短，却让后续动作失去依据。

我会用三个问题检查候选：离开原对话后能否理解；换一个会话后是否仍然可能有用；它的哪部分发生变化时需要修订。能回答这三个问题，通常就能判断信息粒度是否合适。

### 用户说明与模型推断各自有什么依据

用户明确说明的偏好，与模型根据一次行为猜出的偏好，证据强度不同。一次选择 pnpm，可能只是沿用当前仓库；持续维护某个仓库，也未必说明用户认同其中全部技术决策。

因此，提取提示把注意力放在用户的稳定背景、明确表达和持续项目上。来源关联则给后续检查保留入口：这条内容是用户直接说明的，还是从一段活动里提炼出来的，可以继续回到对应材料判断。

我也避免用 Agent 的回答证明用户背景。模型建议过某种框架，只能说明建议发生过。后续用户是否采纳、项目是否实际使用，需要来自新的消息或执行材料。

当前字段和提示能够保存来源、约束提取对象，但语义判断仍然会出错。抽样检查时，我会特别看一次性指令有没有被推广、模型建议有没有变成用户决定、项目局部信息有没有变成全局偏好。这几类错误进入长期记忆以后，传播范围比一次普通回答更大。

### 稳定程度决定维护方式

提取结果区分 `permanent` 和 `temporary`。长期工作习惯可以标记为相对稳定的信息；一个持续几周的项目、近期事项或阶段性安排，则需要生命周期。

这个分类服务于后续维护。临时事项可以按到期时间和使用情况退出召回；稳定偏好通常要等新的说明来修订。它们都可能变化，只是变化的触发条件不同。

例如“用户正在准备十月底发布”需要保留计划的时间；“用户维护一个使用 TypeScript 的个人项目”可以保留更久。把它们拆开，发布计划结束以后，项目背景仍然可以继续使用。

稳定程度也会影响来源要求。持续项目虽然变化较快，但可以有明确目标和阶段；一个长期偏好则最好来自用户稳定的表达。给模糊推断贴上 `permanent`，只会延长它影响后续回答的时间。

我把这两个类别看作维护策略的输入。它们告诉整理流程应该怎样处理时间和清理条件，事实是否仍然成立，还要结合新证据与当前任务判断。

## 事实存储：正文、来源和向量分别承担什么

一条事实进入系统之后，后续会被查询、编辑、去重、合成或归档。要支持这些操作，存储结构就需要表达“这是什么信息”和“它经历了什么”。

### 元数据来自具体操作的需要

我保存的主要字段如下：

| 字段 | 后续哪一步会用到 |
| --- | --- |
| `id`、`content` | 精确定位条目，读取、编辑或删除正文 |
| `threadId`、`messageId`、`userId` | 回到对话来源，识别属于哪个人和用户空间 |
| `source`、`tags`、`importance` | 表达来源与主题，为整理提供排序依据 |
| `durability`、`expiresAt` | 判断生命周期和临时信息的退出条件 |
| `originAnchors` | 保留原消息发送时间与时区，解释相对日期 |
| `createdAt`、`updatedAt` | 记录数据何时保存、何时发生修改 |
| `accessCount`、`lastAccessedAt` | 观察使用情况，辅助临时清理和保留选择 |

这些字段分别回答不同问题。保存时间能定位一次写入，原消息时间能解释用户当时说的“明天”；访问次数能说明被检索过，却无法直接证明它帮助了回答。区分这些含义，维护规则才有可靠的输入。

来源还影响用户纠正信息的成本。用户看到一条奇怪的偏好，能回到原对话，就可以判断是提取时扩大了范围，还是自己后来改变了要求。只有一句孤立结论时，这种纠正会困难很多。

### 正文表达含义，元数据支持操作

我会尽量让正文自己带上主体、对象、范围和必要的时间。这样，一条事实进入模型上下文以后，无需依赖某个界面或隐含字段就能被理解。

元数据则保存适合程序处理的内容：用 ID 定位，用来源关联原消息，用到期时间筛选临时条目，用用户空间控制归属。把所有条件都藏进标签，正文又写得很泛，容易让模型只看到不完整的结论。

反过来，把所有操作信息都堆进正文，也会增加检索噪声。数据保存时间、访问次数和维护批次主要供系统使用，只有涉及时间解释或检查时，才需要以明确的说明一起呈现。

合成以后，这种分工仍然要保持。正文融合可以共同表达的信息，来源锚点继续关联原始材料。新句子写得更连贯以后，仍然需要知道它由哪些证据支持，才能在未来纠正其中一部分。

### SQLite 保存事实，向量提供一种查找方式

我用 SQLite 保存正文和元数据。个人 Agent 经常需要本地读取、修改、备份，以及把条目和对话关联起来，这些都是数据库可以直接承接的操作。

语义检索使用 sqlite-vec，将 `memory_id` 与 embedding 关联。向量由正文计算得到；更换模型、修改正文时，可以用正文重新生成它。因此，正文与元数据承担事实存储，向量承担语义索引。

这个区分在处理失败时很实际。当前新增流程会保存事实行，再保存向量；两步之间发生异常，就可能出现正文已存在、语义检索暂时找不到的状态。排查时应该先检查事实行和向量是否对应，再判断是否需要补建索引。

更换 embedding 模型也要遵循这个关系。同为 384 维，只说明向量长度相同；不同模型给坐标赋予的语义可能完全不同。模型切换时需要重建相应向量，把新查询和旧向量混在一起比较，会得到难以解释的分数。

本地索引让数据维护比较直接，代价是应用需要承担模型准备、索引重建和一致性检查。这些成本随记忆使用持续发生，设计时要和查询效果一起考虑。

### 一次修改会影响正文和索引两份状态

编辑记忆时，新的正文需要新的向量；删除和归档时，正常检索也要停止使用对应向量。对用户来说这些都是一个动作，内部却涉及两份关联状态。

因此，我把事实行与向量行是否一致看作一类独立问题。正文存在而向量缺失，会造成语义漏召回；正文已经修改、向量仍描述旧内容，则可能按照旧主题命中，却返回新的句子。后者尤其难从结果列表直观看出来。

当前写入和更新包含分步数据库操作。事实存储与索引的职责虽然已经分开，操作的完整性仍然需要逐个路径检查。需要增强一致性时，可以把能够一起提交的数据库变更组织成事务，把模型生成向量等外部等待放在提交之前完成。

保留正文提供了修复索引的材料。完整的恢复流程还需要发现缺失、确定重建范围、执行重建和确认结果，每一步都要有具体实现。检查数据与索引的对应关系，才能判断恢复是否真正完成。

### 索引重建期间怎样继续提供可解释的结果

切换模型、维度或重建数据时，会暂时出现索引准备中的状态。当前重建流程包含清理旧向量再生成新向量的阶段，因此这段时间的召回覆盖需要按实际进度理解。

这让我在选择索引实现时，同时考虑重建成本与可用性。小规模个人记忆可以接受一次明确的重建过程；数据变多以后，维护窗口、后台进度和失败重试就会影响日常体验。

若进一步改进，我会优先考虑让旧索引与待构建索引的生命周期明确：构建完成并核对以后再切换查询。这样可以把“新索引尚未准备好”和“没有相关记忆”区分开。当前正文仍然保留，为这类改进提供了基础。

## 写入去重：新信息究竟增加了什么

用户会多次强调同一偏好，提取模型也可能把一句要求换几种表达。任由这些内容累积，Top-K 很容易被同一个意思占满。

因此，自动新增事实之前，我先找到相近旧条目，再判断信息是否已被覆盖。

### 用向量缩小比较范围，再判断信息增量

写入去重默认取 5 条候选，相似度门槛为 **0.3**。这一步用来找到值得比较的旧事实，之后由工具模型判断新内容是否重复。

比如已有“用户的个人项目使用 TypeScript，以 pnpm 管理依赖”，新提取出“用户的个人项目使用 TypeScript”，新句子的内容已经被覆盖，可以跳过。

如果新句子是“用户的个人项目部署在 Vercel”，则增加了一个独立维度，应当保留。两句话都谈同一个项目，所以向量可能接近；接近程度无法替代信息增量判断。

我也会用带范围的例子检查去重：“个人项目使用 TypeScript”和“工作项目使用 Go”可以同时成立。去重需要保留这些限定，避免把共同的技术主题当成重复内容。

### 重复、纠正和合成需要不同动作

写入去重的输出是保存或跳过。它适合解决新增事实是否已经存在的问题。

用户纠正旧内容时，需要找到具体的旧条目，再编辑或删除它，并保存新说明。当前自动提取可以产生删除与新增操作；按描述删除时，先召回候选，再由模型选择目标 ID。用户手动编辑则可以直接定位条目。

例如“个人项目已经从 npm 迁到 pnpm”，包含状态变化。只新增 pnpm、继续保留旧的 npm 当前状态，会让两条事实在后续竞争；只删除 npm、新增失败，又会让记忆出现空缺。当前删除和新增分步执行，这正是后续增强替换一致性时要处理的问题：把新事实落库和旧事实退出组织成明确的提交。

去重模型调用失败或结果无法解析时，当前流程继续保存新事实。这个选择把风险留给后续维护：库里可能多一条重复，但本轮新信息仍然有保存机会。Sleep 负责进一步处理积累的冗余。

### 去重时，我关心的是覆盖关系

向量检索给出的是相近候选，去重真正要判断的是新内容是否已被旧内容包含。这个关系有方向。

旧事实包含“TypeScript 和 pnpm”，新事实只有“TypeScript”，可以判断新内容已覆盖。交换新旧之后，新增的 pnpm 仍然有信息价值。即使两种情况下文本相似度接近，保存决策也可能不同。

否定和条件会进一步改变覆盖关系。“默认使用 pnpm”和“这个仓库暂时保留 npm”可以同时成立；“只在测试环境启用”与“所有环境启用”更需要区分。去重模型看到候选后，要比较这些限定，才能决定能否跳过。

这也解释了为什么候选数量只取一小批：模型需要逐条比较具体含义，候选太多会增加输入成本和混淆机会。不过，候选数量有限也意味着可能漏掉真正重复的旧条目。后续全库维护承担另一部分覆盖。

### 写入成本与后续读取成本怎样分配

提取、生成向量、查候选、调用去重模型，都增加了一次写入的成本。它们的收益发生在之后：库里重复条目更少，召回更容易覆盖不同背景，后续合成需要处理的冗余更少。

我会把它看作一次信息进入长期使用范围之前的处理。事实保存以后，可能被几十次或几百次读取，因此适当增加写入判断有机会减少长期的重复成本。

代价仍然需要测量。若多数提取都没有新信息，前面的提取门槛应该先收紧；若重复只是在某种来源集中出现，就应该检查该来源的写入方式。每次写入都调用模型，无法自动弥补错误的提取粒度和来源组织。

## 时间：一句话离开原对话以后，怎样保持原意

用户在 10 月 12 日说“三天后发布”，10 月 26 日才导入这段对话。计划指向的是 10 月 15 日。若按导入日期理解，就会变成 10 月 29 日。

这种错误来自两个时间被混用：信息发生的时间，与系统保存信息的时间。

### 原消息时间参与解释，保存时间参与维护

我把原消息发送时间、时区与记忆保存时间分开记录。提取时用原消息解释相对日期，保存时记录这次数据操作发生的时间。

时区也需要跟随原消息。临近午夜的一句“明天”，在另一个时区可能已经跨天。以后读取这条记忆时，只剩服务器当前时间，已经无法完整还原用户当时的含义。

正文中的计划日期、到期日期、实际完成日期，也各有作用。用户说“准备发布”表达意图；后来出现“已经发布”的确认，才有完成证据。时间走过了计划日期，只能说明计划日期已过。

### 时间信息要跟着去重与合成一起走

两条都写着“周五发布”的记录，可能来自不同周、对应不同版本。正文相同，在这里仍然可能是两件事。

精确去重因此结合规范化正文与来源时间锚点。缺少来源锚点的临时事实继续分别保留，避免仅凭一句模糊日期就合并事件。

语义合成也要保留这些差别。可以把同一项目的技术栈和包管理器合成一句；两次发布时间则应保留各自的日期、对象和计划状态。新条目继承相关来源锚点，以便后续继续解释和检查。

时间设计最终影响的是回答里的动词：在做、准备做、做过、已完成。它们决定 Biny 给出的背景是否仍然适用于当前任务。

来源时间的提取也有对象限制。当前流程从用户原始消息中收集时间锚点，跳过压缩摘要。压缩摘要产生于更晚的整理过程，如果把摘要生成时间当成原话时间，前面区分的两个时间又会重新混在一起。

### 新旧信息冲突时，先找它们各自适用的时间

“项目使用 npm”和“项目已经迁到 pnpm”在当前状态上冲突，在项目历史里却可能先后成立。要处理这种情况，需要知道每句话描述的时间和语气。

一条带明确迁移说明的新事实，可以支持当前工具选择；旧状态仍然可能帮助解释历史脚本为什么使用 npm。用户问“现在怎样安装依赖”和“上次迁移前怎样构建”，读取目标不同，适用的信息也不同。

我希望提取与整理尽量保留这种关系，尤其避免把新旧状态拼成一个模糊并列句。当前自动删除、新增和合成能够处理其中一部分，完整的状态演变仍然可以通过原始消息与项目材料追查。

日期也有不同确定程度。“三天后”在来源时间明确时可以转换，“月底找时间”只能表达一个大致计划。把后者自动改写成精确截止日期，会增加原话里没有的承诺。时间解析需要保持原始表达的精度。

因此，保存未知同样有价值。来源时间不明确，就保留未知；完成证据缺失，就保留计划状态。后续有新证据时再补充，比先填出一个看起来完整的时间线更容易维护。

## 召回：把过去的信息变成这次回答的背景

保存之后，记忆的价值要通过一次具体查询实现。当前问题只有一句话，事实库可能已经有几千条。我需要把这句话变成查询，再控制进入上下文的结果。

![事实记忆的生命周期：提取写入、查询召回，以及后台 Sleep 整理](/images/biny-memory/fact-lifecycle.png)

*回答前取用相关事实，回合后吸收新信息，后台整理处理持续积累的维护工作。*

### 查询先对准可能存在的事实

用户问“你记得我平时怎么写文章吗”，库里可能保存“用户偏好直接展开原理与设计取舍”。查询里有“记得吗”这样的对话形式，真正要查的是写作偏好。

所以我加入可选的查询改写，让工具模型生成更接近事实表达的查询。当前策略要求英文搜索表达，例如 `User preferences for technical blog writing`。改写失败时使用原句继续检索。

这增加了一次模型调用，也引入了语义变化的可能。项目名、路径、中文专名一旦被改写成泛称，召回可能更差。因此，改写是否开启，需要拿实际问题观察：原句能找到什么，改写后多找到什么，又丢掉了什么。

接着生成查询 embedding，与事实向量比较。本地方案支持 `multilingual-e5-small` 等 384 维模型，通过 Transformers.js 和 ONNX 推理，也可以配置远端 embedding 服务。

查询向量化会在使用记忆时频繁发生，本地模型可以减少这一环节的网络依赖。模型准备好以后，向量化可以离线完成；查询改写、事实提取与语义合成仍然使用各自配置的语言模型。

### 语义相近能够回答哪一类问题

向量检索适合处理表达变化：用户问“怎么写文章”，事实写“技术博客的表达偏好”，两者没有完全相同的关键词，仍然可能在语义空间里接近。

精确名称和编号则有另一种需求。查询某条报错、某个命令参数或某次 PR 时，一个字符的差别就可能改变目标。这类任务通常需要继续搜索原文，确认命中的内容包含准确标识。

我因此保留不同的读取入口。事实语义搜索负责找可复用背景，聊天全文搜索负责定位原句，项目与活动材料负责进一步恢复上下文。Agent 可以根据问题调整查找方向。

同一句请求也可能需要多个背景维度。“按我平时的表达，把这个项目的设计写清楚”同时涉及写作偏好和项目设计。当前自动召回使用一个查询，返回结果可能集中在其中一边。复杂任务要继续主动检索，分别补齐缺少的材料。

这类情况让我把召回覆盖与条目相似度分开观察：一个结果列表里的每条都很相近，整体仍然可能只覆盖问题的一部分。评估时需要检查不同信息需求是否得到满足。

### Top-K 和门槛控制两个不同的量

Top-K 控制最多返回几条，门槛控制哪些条目有资格进入结果。假设有二十条事实超过门槛，Top-K 为 5 就取其中最接近的五条；如果只有两条达标，结果就应该只有两条。

这两个参数要按入口分别理解。当前配置的默认值如下：

| 入口 | 候选数量 | 相似度门槛 | 这一步要解决的问题 |
| --- | --- | --- | --- |
| 回答前自动召回 | 5 | 0.1，可配置 | 为当前回答补充可能相关的背景 |
| 新事实写入去重 | 5 | 0.3 | 找到值得进一步比较的旧事实 |

0.3 对应写入去重入口；自动召回读取自己的配置，代码中的默认值为 0.1。显式搜索也由调用参数决定门槛。这些数值分别约束不同的查询任务。

余弦相似度还需要结合模型理解。0.3 表示当前向量空间中的一个相似度分数，“有 30% 的概率正确”则是另一种含义。使用新的模型或新的记忆样本以后，要重新观察分数分布。

我调整参数时会看具体结果：门槛降低后，新增候选是否真正帮助回答；Top-K 增大后，是否只是重复偏好变多。数值的意义来自实际查询集。

Top-K 还会受到条目粒度的影响。同一个项目拆成十条短句，其中五条占满结果，就可能挤掉写作偏好。把十条全部合成长段，又会让任何一个局部问题都带入大量额外背景。提取粒度、整理方式和查询参数需要一起评估。

我会保留一组确实需要背景的问题，也保留一组无需历史的问题。前者观察漏召回，后者观察是否出现不必要的注入。只测试“记得我的某个偏好吗”，很容易高估一个低门槛配置的收益。

对于分数接近门槛的候选，我会进一步检查文本。它可能是弱相关但有帮助的背景，也可能只是同一个技术主题。前者是否值得进入上下文，取决于任务需求和其他候选；后者则可能增加解释负担。

### 返回数量小，扫描成本仍然可能增长

当前向量查询的核心可以写成：

```sql
SELECT
  memory_id,
  1 - vec_distance_cosine(embedding, ?) AS score
FROM memory_embeddings
WHERE score >= ?
ORDER BY score DESC
LIMIT ?;
```

这里计算候选向量的余弦距离，再排序、截取结果。N 条向量、每条 d 维，距离计算量约为 O(Nd)，另外还有排序成本。`LIMIT 5` 控制返回结果，距离扫描仍然随候选规模增长。

个人记忆规模下，我先使用这种容易理解和检查的实现。后续是否需要分区或近似近邻索引，应由查询延迟和记忆规模决定。同时要观察索引复杂度带来的重建、更新和排查成本。

范围过滤也影响实际效果。当前流程先取向量 Top-K，再按关联用户、会话或标签过滤。如果前五条里有四条属于其他范围，过滤以后只剩一条；正确范围里的第六条已经没有机会返回。

这说明范围约束同时关系到信息归属和召回覆盖。要提高多用户场景的覆盖，应该让允许访问的范围尽早参与候选选择，或者扩大候选后再截取有效结果。当前实现的先后顺序需要在评估里单独观察。

数量增长也会改变参数选择。在很小的记忆库里，返回五条可能已经覆盖多数背景；库变大以后，重复条目、同主题项目和不同时间的状态都在竞争相同名额。保持 Top-K 不变，召回难度仍然会增加。

因此，我把库的维护质量与检索性能一起看。清理确定重复、合成互补背景，可以改善有限名额的使用效率；索引优化则减少找出候选的时间。两项分别改善结果与成本，不能互相替代。

### 自动召回之后，还需要继续找证据的路径

一次自动召回由当前问题触发，结果天然只覆盖少量相关背景。我会在注入的记忆块里告诉模型这一点，并提供继续查找的方向：事实搜索、聊天历史、项目材料和活动记录。

例如“我平时怎样写技术博客”，适合从偏好事实开始；“我上次具体用了哪条命令”，应该继续查原始消息或终端记录；“为什么否定那个方案”，往往需要恢复当时的约束与讨论。

这样，自动召回承担常见问题的低成本起点，复杂任务可以继续扩大取证范围。召回条目提供背景，涉及当前项目状态和重要动作时，再用相应的原始记录确认。

主动检索还承担消歧义的作用。当前请求只说“那个项目”，历史里存在多个候选，继续读取最近相关会话或项目材料，能帮助确定指向。直接依据一个相似度最高的条目作决定，容易把检索排序误当成身份确认。

对于记忆里缺少的信息，继续查找也要有停止条件。找到原话、当前文件或明确结果以后，证据已经能够支持任务，就可以继续工作。反复扩大搜索范围会增加等待，也可能引入更久远、更弱相关的材料。

## 上下文装配：检索结果怎样参与一次回答

检索返回条目之后，还需要决定怎样呈现给模型。这里连接了记忆系统和 Agent 的实际行为：同一条事实，以什么时间、来源和范围进入上下文，会影响模型如何使用它。

### 让正文与解释正文的坐标一起进入

当前注入块除了事实内容，还会说明记忆保存时间、原消息时间锚点，以及保存时间不能替代事件时间。这些信息帮助模型解释正文里的相对日期和状态。

只注入一句“用户计划周五发布”，模型需要自己猜测是哪一个周五；加上来源消息的时间，就有了解释依据。如果来源未知，也明确保留未知，避免把数据写入日期当成用户承诺日期。

来源说明还影响后续查证。当事实与当前文件不一致时，模型可以继续读取项目现状；当用户问的是过去为什么做某个选择时，可以回到相应对话。记忆块因此需要让模型知道自己看到的是哪一种材料。

当前召回流程也返回本轮使用的记忆 ID 与正文，供界面展示检索结果。用户能看到参与回答的背景，就更容易指出“这个项目已经不用它了”或“这条偏好只针对博客”。反馈有具体对象，纠正成本会低很多。

### 不同来源的内容需要按任务解释

当前请求表达用户这一次的意图，稳定偏好提供默认背景，项目材料描述工作对象，历史活动说明过去发生过什么。把它们放进同一轮输入以后，仍然需要保留这些角色的区别。

例如用户明确要求写一篇详细设计文章，即使长期偏好提到“表达简洁”，这次的详细要求仍然决定展开程度。偏好可以帮助减少套话和重复，不能把任务需要的推导一起删掉。

项目状态也一样。旧记忆记录某个版本使用 npm，当前仓库已经切到 pnpm，就应该结合仓库现状处理当前构建。历史记忆继续可以用于解释旧脚本，但它描述的时间和对象需要被看见。

我希望记忆在这里承担减少重复解释的作用。遇到明确更新、范围不符或来源冲突时，要继续判断适用性。注入更多背景只是提供了材料，材料之间的关系仍然需要解释。

### 条目数量与实际输入体积要分别控制

Top-K 限制返回条数。一条事实可能只有几十个字，也可能已经合成一段较长说明，所以相同的 Top-K 对应的 token 量会变化。

固定加载的文件、当前任务摘要和召回事实也共同占用上下文。某一层持续增长，会减少其他材料可以使用的空间。因此，我在设计上分别关注固定背景的长度、任务现场的体积和本轮额外召回的规模。

当前各入口通过自己的选择规则控制内容，Top-K 和近期文件窗口承担了一部分限制。若要进一步建立统一预算，还需要在装配时统计实际长度，决定哪些材料保留全文、哪些材料只留下入口。这属于下一步可以明确收敛的控制点。

这里优先保留的是当前任务直接需要的信息。稳定背景可以缩短，历史细节可以按需继续读取，最新约束和关键验证结果则需要具体。预算分配跟随任务，而非每层机械地占相同篇幅。

### 召回失败时，主任务怎样继续

自动事实召回先检查是否启用、当前会话是否为隐私模式、是否有可用 embedding 服务。缺少服务或查询异常时，当前入口返回空记忆块，并提供相应进度状态。

这样，记忆查询失败不会迫使本轮回答携带一个半成品结果。Agent 仍然可以依据当前会话、工具结果和其他已加载材料完成能够完成的部分。

不过，“没有找到相关条目”“服务不可用”和“索引还在准备”描述的是不同情况。排查时要结合运行状态，无法只看空结果判断库里没有信息。界面中的检索进度与日志在这里承担了说明原因的作用。

这也是我将事实检索与主任务分开处理的理由之一。记忆能够改善任务连续性，基础交互仍然需要在记忆服务暂时不可用时给出可解释的行为。

## Sleep：记忆库为什么需要定期重新整理

写入去重每次只看到新条目和少量候选。库里仍然会积累手动新增、不同回合的零散描述、已经结束的事项，以及可以合成的互补信息。

这些问题具有全局性。把全库扫描和语义合成放进每次回答，会让回答时延随记忆库增长。因此，我把它们交给独立的 Sleep 流程。

### 按确定性和成本安排整理顺序

一次整理依次处理精确重复、过期临时事实、语义相近的候选。先做能用规则判断的部分，缩小后续需要计算距离、调用模型的数据量。

精确去重先做 Unicode NFC 规范化、合并连续空白、去掉首尾空白，再结合来源锚点分组。大小写和标点仍然保留，因为它们在名称、命令和条件里可能有含义。

需要保留一个条目时，排序综合考虑稳定程度、重要性、访问次数和更新时间。永久标记提供明显的排序优势，重要性和访问次数继续参与计算，访问次数受到上限约束。这个顺序让频繁被检索的重复条目拥有一定优势，同时避免访问量无限累积后主导所有选择。

临时事实的清理有两条条件：明确到期时间已经过去，或者创建超过默认 30 天且从未被检索使用。当前第二条仍然会独立判断，所以即使设置了未来的到期时间，也要结合年龄和访问情况理解结果。

访问计数记录的是被检索到的次数。它可以作为清理信号，但用户是否认可、事实是否正确，还需要别的证据。因此，这里归档的是满足维护条件的临时条目，后面保留恢复窗口。

### 维护规则为什么要有明确的触发条件

精确重复和过期条件能用数据直接判断，结果比较容易解释。用户问某条内容为什么退出召回，可以回答正文与来源相同，或者临时事实满足了具体清理条件。

语义相近则具有更大的不确定性。两条内容可能重复，也可能互补、矛盾，或只是围绕同一个主题。把它留到后面的模型判断，能够让维护过程先完成依据明确的部分。

顺序也影响成本。先归档确定重复，再做向量比较，就减少了需要扫描的条目；先处理临时事实，可以降低已经失效的事项进入合成的机会。每一步既完成自己的任务，也改变后续输入。

因此，我会记录各阶段数量。一次运行若有大量条目在精确层被清理，可能说明某个写入来源正在产生重复；如果主要消耗发生在模型合成，可能需要检查提取粒度、候选门槛和批次构成。维护统计也可以反过来帮助改进前面的写入过程。

### 从相似候选到合并，中间还有语义判断

剩余事实进入向量比较。默认以 0.75 作为候选关联门槛，用并查集把相连条目分成簇；后续再选择高相似处理或模型合成。

这个分组有一个容易影响结果的性质：A 接近 B，B 接近 C，就可能进入同一簇；A 与 C 仍然可能相距很远。候选簇适合减少比较范围，簇内每条信息的关系还要继续检查。

当前高相似分支使用 0.95，并结合簇中是否存在临时信息或时间锚点选择处理路径。实现用簇内最高的关联分数触发这一分支，因此一个簇里的所有条目并不都满足两两 0.95。这也是后续收紧快速归档条件时，我会优先检查的地方：每条待归档事实与保留事实的关系要能单独成立。

带时间证据或临时状态的候选进入语义判断。这里尤其要保留项目范围、否定条件和计划状态，因为这些信息很短，却能改变整句话的意思。

分簇使用连通关系，具有很直接的实现收益：只要两个条目达到候选门槛，就把相关部分放进同一组。但门槛降低以后，一条较泛的描述可能连接多个本来区别很大的项目。

例如“用户维护多个 TypeScript 项目”可能同时接近两个具体项目的事实。把三者放进同一簇有助于一起检查，整理时却必须继续保留两个项目的身份。连通性表示值得共同审视，具体合并关系还要逐条成立。

这让我同时观察簇的大小和内容跨度。一个很大的簇可能来自大量重复，也可能来自过于泛化的事实。单纯提高门槛能缩小簇，但也可能漏掉表达差异较大的重复。因此，候选生成与后续合成要结合具体样本调整。

### 合成要保留哪些信息，可以用例子检验

假设一个候选批次里有：

```text
事实 1：用户的个人项目使用 TypeScript。
事实 2：用户的个人项目用 pnpm 管理依赖。
事实 3：用户的工作项目使用 Go。
```

前两条可以合成“用户的个人项目使用 TypeScript，以 pnpm 管理依赖”。第三条继续独立保留。合成减少的是重复表达，项目归属和独立信息仍然存在。

模型提示要求保留原信息、避免混合无关对象，并保留时间区别。程序检查返回结构，把删除 ID 限制在本批候选里，并拒绝没有合成结果却要求清空整个簇的输出。

结构检查能限制模型操作哪些条目，合成是否遗漏含义则需要内容评估。例如“仅测试环境关闭认证”少了“仅测试环境”，句子仍然通顺，风险却发生了变化。评估要覆盖这类很短的限定条件。

模型批次默认 20 条，过大的簇会跳过。限制批次是为了控制一次语义判断的输入规模；它无法消除前面生成候选的成本。当前候选生成采用两两向量比较，距离计算量约为 O(N²d)，记忆量增长以后，这一步需要单独优化。

### 合成以后，元数据怎样继承

合成的新正文仍然需要维护信息。当前流程合并来源锚点和标签，增加整理标记，访问次数取候选中的最大值，并使用保留候选的重要性。

访问次数取最大值有一个实际含义：同一信息以多种说法被重复检索，合成以后不会因为简单相加而获得成倍的使用量。它保留曾经使用较多这一信号，同时减少重复条目对统计的放大。

来源锚点取并集，则让新句子继续带着产生它的多段材料。后续发现某个范围错误，可以回到相关原消息检查；继续合成时，时间规则也有原始坐标可以使用。

这些继承规则仍然各有含义。重要性来自候选的排序选择，访问次数表达检索经历，来源表达依据。把它们一起保留以后，仍然需要分别解释，尤其不能用高访问量代替事实正确性的判断。

### 合成失败时，数据要处于什么状态

合成包含一段等待模型的时间，也包含生成新向量、保存新条目、归档旧条目等多步操作。任意一步失败，都可能留下部分完成的状态。

当前实现先尝试保存合成事实，再归档指定旧条目。各次合成写入失败会被记录，但并未整体阻止后续归档。因此，提示里要求保留全部信息，并不能直接保证每次执行后活动事实库都保留了全部信息。

我把这看作这条维护链路需要补强的提交条件：新事实成功保存之后，才能让被替代的旧事实退出；等待期间若用户编辑了候选，也要重新确认操作仍然适用。将这些条件落实到提交过程，才能让语义正确与执行正确同时成立。

已有归档机制为检查和恢复保留了入口。归档保存原正文、元数据、原因、整理批次，以及合并后的去向。条目退出正常召回以后，用户仍然可以查看和恢复。

默认保留期是归档后的 30 天。按归档时间计算，可以让一条保存了很久、刚刚被整理的事实仍然有完整的检查窗口。

归档还让日常查询和维护历史分开。正常召回只看仍然参与使用的事实，用户检查整理结果时则可以查看退出原因和原正文。这样，检索规模可以下降，整理过程仍然有材料可追查。

恢复意味着把某条退出的内容重新带回使用范围。恢复以后还需要关注是否与合成结果重复、索引是否准备好，以及下一次整理会不会再次命中相同条件。可恢复提供了操作入口，维护规则的错误仍然需要单独修正。

我保留预览也是为了降低调整规则的试错成本。先看拟归档与拟合成内容，可以发现门槛是否过宽、范围是否混合。预览仍然需要完成相应分析，它节省的是直接修改数据带来的检查与恢复成本。

### 调度要考虑应用可能关着，也可能运行失败

Sleep 默认在本地时间 03:00 后检查当天是否已经成功整理。应用错过时点以后，再次运行仍能补做当天的维护。同一服务实例通过运行状态避免重入，连续失败时暂缓继续尝试。

这套调度适合随桌面应用运行的维护任务。当前触发依据是时间和运行记录；如果希望避开用户正在进行的重任务，还需要增加实际的空闲判断。

每次运行记录状态、各阶段处理数量与模型 token，并提供预览查看拟归档、拟合成的内容。预览让规则调整有可比较的结果，运行记录则帮助定位失败停在哪一步。

我关注的运行指标也从这些步骤产生：扫描了多少条、归档了多少条、合成消耗多少、是否出现异常大的簇，以及恢复时能否找到原事实。条目数下降只是其中一个结果。

启动时，当前流程还会把此前中断的运行标记为失败。这让新的运行能够识别上一轮并未正常结束，避免一直停留在看似进行中的状态。需要恢复具体数据时，再依据归档与运行记录检查已经完成的步骤。

同一实例的防重入解决的是当前进程里重复启动的问题。将来若允许多个维护执行者同时处理同一份数据，还需要额外协调提交范围。当前桌面应用的运行方式与这种扩展场景，应该分别设计。

维护任务的取消也要落实到阶段之间。停止继续扫描、停止发起新批次，以及保留已经提交的结果，分别对应不同状态。把每阶段数量和最终状态留下来，才能解释取消时哪些工作已经发生。

## 文件记忆：哪些背景值得每次直接读

语义召回的结果取决于查询。对于用户画像、近期经历这类经常需要的背景，每次都等当前问题恰好命中，会增加使用的不确定性。

此外，一段连续经历通常需要按顺序理解。把“项目为什么开始、经历过哪些选择、现在重心在哪里”拆成许多独立句子，查询时可能只取到其中几句，读者还得重新补出关系。

这些需求让我保留文件记忆，让经常一起阅读的信息有一个固定位置。

### 按阅读频率和内容关系组织文件

`USER.md` 保存用户画像，`MEMORY.md` 保存长期备忘，`memory/YYYY-MM-DD.md` 保存按日期组织的经历，`SOUL.md` 表达 Agent 的行为风格。

这些文件的更新频率和使用方式不同。用户画像变化较慢，适合维护相对稳定的背景；日记增长快，适合保留近期进展；长期备忘承接反复需要的连续说明；行为风格则影响表达和互动。

常用加载流程读取长期备忘以及今天、昨天的日记。两天的窗口让刚发生的事情容易延续，按日期保存的旧记录仍然可以在需要时读取。

例如昨天写了“已经排查到向量维度不一致，今天继续重建索引”，今天开启会话时，近期日记能直接提供这个衔接。三个月以前的相同记录则适合在查那次故障时再读取。

### 文件的边界，来自不同内容的更新节奏

用户画像、长期备忘和日记如果都写进一个文件，最先发生的问题通常是更新方式混杂。修改一个长期背景，需要在大量历史记录里寻找；追加一天的经历，又会让每次加载都变长。

按用途分开以后，画像可以围绕稳定背景修订，长期备忘可以围绕当前仍然重要的说明维护，日记则按日期追加。用户查看和编辑时，也更容易判断一段内容应该放在哪里。

日记的时间顺序还保留了变化过程。一项决定在周一提出、周三修改，可以通过两个日期的记录理解。长期备忘则更适合描述目前持续有效的背景。两者共同使用时，既有当前说明，也有追查过程的入口。

行为风格又有独立的使用目的。`SOUL.md` 描述 Agent 怎样表达和互动，`USER.md` 描述用户背景。将两种内容分开，可以分别维护“怎样协作”和“与谁协作”，避免用户某次对话中的状态不断进入 Agent 的长期行为设定。

文件结构因此可以保持直观：

```text
USER.md                用户背景与画像
SOUL.md                Agent 的表达与行为风格
MEMORY.md              经常需要的长期说明
memory/YYYY-MM-DD.md   当天的经历、进展与记录
```

读取时，文件名给出内容类型，日期给出时间入口，正文保留连续叙述。这个组织方式对机器和用户都有较低的理解成本。

### 固定加载的收益，来自持续支付上下文成本

直接加载省掉了每次挑选的过程，文件增长却会让每个回合承担更多输入。长期备忘里多写一段，成本会在后续所有加载它的回合里重复出现。

因此，我希望长期备忘保持能快速读完的背景，把细节留给日记、原会话和项目材料。决定一段内容放在哪里时，要看它是否经常整体参与理解，以及是否值得反复占用上下文。

文件也让用户可以直接阅读和修改记忆。用户发现某段画像已经过时，可以编辑原文；想保留一段连续说明，可以按自己的语言组织。

文件提供连续阅读，事实条目提供细粒度检索。两种使用方式并存，也带来了跨层更新的问题，后面再具体展开。

### 两天的窗口怎样影响连续性与遗漏

今天和昨天的记录具有较高的近期使用概率，直接读取能减少用户重复介绍。窗口继续扩大以后，输入成本会稳定增加，额外内容的使用概率却可能下降。

这个窗口表达的是默认读取策略。用户明确问上周某天的事，查询就应该转向对应日期；问某个项目的长期演变，则可以结合项目材料与相关日记。近期文件提供起点，完整历史仍然保存在其他可查位置。

日期入口也有语义检索难以完全替代的作用。查“10 月 12 日的工作”时，日期范围能够直接确定材料集合。查“哪天开始讨论索引迁移”时，内容搜索更有帮助。两个入口分别承接已知时间和已知主题的查询。

我会检查窗口之外的信息是否还能被找回。自动加载范围变小以后，若旧材料缺少清晰的文件名、索引或主动读取入口，减少的输入成本就可能转化为漏找历史的成本。

### 修改一段文件，怎样避免留下矛盾背景

文件能够被用户直接编辑，这是它的重要使用方式。用户可能把技术栈从 npm 改为 pnpm，也可能删除一段已经不适用的画像。

当前文件与事实条目分别维护，直接编辑文件不会自动完成事实库的相应修订。因此，一个更改可能只发生在固定加载的背景里，旧条目仍然通过语义召回出现。

我在处理这种冲突时，会先确定这次任务要使用哪种状态。用户刚刚明确修改的项目说明，对当前操作有直接意义；旧事实可以进一步编辑或删除，原始消息继续提供历史依据。跨层纠正要落到具体条目，避免只在当前回答里解释一次。

若以后增加同步流程，需要定义文件片段如何对应事实、改动怎样识别、删除怎样传播，以及冲突如何呈现。文本位置会随编辑移动，同一段说明也可能生成多条事实，自动同步本身需要明确的数据关系。

这也是我保留现有职责划分时要承担的维护成本。两种形态各有使用收益，重复内容则需要可见、可查和可纠正。

## Crystal：零散材料怎样围绕同一个对象积累

一个项目会被反复提到。早期可能只有名称，后来出现目标、参与者、版本、决定和参考材料。每条事实都能独立查询，却还缺一个围绕项目整体查看材料的入口。

第一次提到名称就建完整卡片，容易产生大量空壳；等到用户主动整理，又会错过许多已发生的讨论。Crystal 用来承接这段逐渐积累的过程。

### 多次出现，先积累成形的证据

我先识别具体称呼与别名，累计出现次数、不同回合，以及跨会话或跨日期的分布。仅在一轮里反复出现一个名字，通常只能说明当前话题集中；跨几个回合或日期持续出现，才更能说明它值得长期组织。

默认的轮廓门槛是 4 次记录、3 个不同回合、2 个分布；进一步形成核心需要 8 次记录、5 个不同回合、2 个分布。这里的分布使用会话数与日期数中较大的一个判断，同一回合的重复记录会被跳过。

次数用于发现反复出现的对象，回合数用于避免单次讨论主导结果，分布用于识别持续性。三个条件共同决定什么时候形成候选，比单看词频多保留了两种信息。

### 名称能够聚合材料，也可能造成误聚合

一个项目可能同时有正式名称、缩写和日常叫法。若每个叫法都形成独立对象，材料会被拆散；若只按字符串相近合并，又可能把同名项目或不同版本混在一起。

因此，名称处理首先服务于对象身份。能够识别具体称呼以后，再根据上下文确认这些称呼是否指向同一件事。一次讨论里同时出现的两个名字，也可能是被比较的两个方案，关系需要从材料里确认。

我会特别检查两类情况：同一项目换了简称之后材料是否仍然聚拢，以及两个主题相近的项目是否仍然保持独立。前者影响完整性，后者影响准确性。

这与事实去重的粒度不同。一条事实可以只表达一个项目的某项背景；Crystal 需要持续维护这个项目是谁、有哪些称呼，以及哪些材料属于它。对象身份一旦错了，后续字段就可能从多个项目里吸收信息。

名称本身也要过滤。“这个项目”“方案”“问题”缺少稳定指向，通常无法作为长期对象的名字。别名则帮助把不同称呼关联到同一个对象，后续还需要检查同名对象是否被误合并。

### 候选卡片先关联材料，再补字段

对象形成核心后，候选卡片关联此前的会话材料。以后新增相关讨论时，继续追加来源引用。这样，卡片上的描述可以追溯到具体材料。

字段随对象类型变化。项目需要目标、范围、交付物、版本和来源；概念需要定义、包含与排除的范围、例子和来源；流程需要触发条件、输入、步骤、输出与失败处理。

我采用这些字段，是因为“了解一个对象”最终要落到能够回答具体问题。只有一个项目名称和一段流畅介绍，仍然很难判断当前交付什么、哪些内容属于范围、结论来自哪里。

字段就绪检查因此同时看值、来源和冲突。字段有文字却没有来源，仍然缺少依据；不同材料给出冲突结论，也需要先处理冲突。满足条件后，系统才提示候选已经具备进一步整理的条件。

### 为什么字段随类型变化

项目、概念、规则和流程需要回答的问题不同。项目强调目标与交付范围，概念强调定义与例子，规则强调适用条件与例外，流程强调触发、输入、步骤和失败处理。

如果所有对象都只放“名称加介绍”，卡片很容易写得流畅，却难以支持实际工作。一个流程介绍再长，缺少失败时怎样处理，Agent 仍然无法据此执行；一个规则缺少例外，就容易被推广到不适用的场合。

类型字段把“理解这个对象还缺什么”变得具体。缺少项目来源，就继续查材料；规则条件互相冲突，就先处理冲突；流程缺少输出，就还需要知道怎样判断完成。

当前就绪检查验证字段有值、有来源引用，并检查冲突标记。引用是否真正支持字段内容，仍然需要阅读材料判断。程序检查提供了最低结构条件，内容整理决定卡片是否可靠。

我希望卡片逐步成熟。先形成候选，再积累材料、补全字段、处理冲突，这样每一步都对应新的依据。被频繁提及只是进入整理范围的信号，完整程度需要由内容本身证明。

### 新材料怎样继续找到已有对象

名称匹配可以覆盖直接提名的讨论。用户有时会沿用简称，或只谈某个已经明确的子问题，所以还需要语义关联作为补充。

当前语义扫描针对进入整理范围的候选卡片，比较新消息与卡片名称、已有字段组成的文本，将相关回合加入候选材料。它扩展的是材料范围，材料里的内容还需要经过后续整理才能成为字段结论。

例如卡片叫“Biny 记忆系统”，用户只说“继续处理昨天那个临时事实的过期逻辑”，语义关联可能帮助找到这张卡。与此同时，“另一个项目也有过期逻辑”又可能造成误关联。保存来源引用，可以让这类问题有检查入口。

长期没有更新的对象可以休眠，后续再次出现时唤醒。这个状态表达关注频率的变化，已经积累的材料仍然保留。

Crystal 的效果要从对象能否被完整理解来判断：名称是否稳定，相关材料是否聚拢，字段是否有来源，以及冲突有没有被看见。提及次数只负责帮助发现值得组织的对象。

### 新材料进入以后，已有结论怎样变化

项目会出现新版本，规则会增加例外，流程也可能在执行中暴露缺口。新材料与已有字段一致时，可以补充依据；增加细节时，可以扩展字段；与已有内容冲突时，则需要判断是状态改变还是对象关联错误。

例如项目字段写“仅支持本地运行”，新材料讨论远端部署，可能意味着新版本已经扩展，也可能只是一个尚未采纳的建议。直接把字段更新成“支持远端部署”，会跳过从讨论到决定再到实现的区别。

保留材料引用，让整理能够继续检查这些状态。字段描述当前理解，材料保留形成理解的过程。未来重新整理时，可以从引用继续阅读，判断哪些结论需要修订。

休眠则处理关注频率下降。一个项目结束后，名称可能长期不再出现，但它的目标、决定和材料仍然有历史价值。将它移出活跃关注范围，可以减少日常处理，同时保留以后重新查找和唤醒的能力。

因此，Crystal 同时存在发现、整理、使用和休眠几个阶段。各阶段使用的信号不同：发现依赖持续出现，整理依赖内容与来源，使用依赖当前任务，休眠依赖近期活动。这些信号分开，卡片才能随着项目生命周期变化。

## Activity：从电脑上的过程，提取可查的工作记录

聊天只能提供用户说出来的部分。实际上，大量工作发生在编辑器、终端和浏览器里：查了哪些材料、在哪个错误上停留、上午围绕哪个项目切换应用，用户很少逐项复述。

为了回答“那天我做了什么”，我需要保存另一种输入：按时间排列的电脑活动。

### 先用事件和变化组织活动片段

应用焦点、窗口标题、浏览器访问和画面变化提供事件线索，截图保存某些时刻的画面，本地 OCR 再把画面转成可检索文字。

这些输入承担不同作用。应用名称告诉我在哪个工具里，标题与网址帮助定位对象，OCR 可能给出错误文本、文档标题或项目名称，时间戳把它们放回同一段过程。

采集需要控制频率。连续打字、窗口微小变化或重复页面可能制造很多近似样本，所以流程使用去抖、采样与画面变化判断来控制截图，后续分析也会去掉高度重复的 OCR 文本。

单个事件很难表达一项工作。系统先把活动组织成片段，再合并相邻、间隔较短且应用有交集的待分析片段。这样，一次从浏览器查资料、切到编辑器修改、再去终端验证的过程，有机会被放在共同上下文里理解。

### 采样频率决定能留下多少证据

电脑活动连续发生，截图只是离散采样。采样更密，越容易留下短暂画面，也会保存更多重复内容；采样更疏，成本下降，某些错误提示或操作结果可能在两次采样之间消失。

所以，固定节奏之外，还需要利用应用切换、输入停顿和画面变化等信号。它们提高某些时刻被记录的机会，但仍然只能形成部分观察。查询结果需要按已保存证据解释。

OCR 将像素转换成文字，又引入一层信息选择。它保留错误消息、标题和正文，布局、图表关系与被遮挡内容可能难以完整表达。活动摘要有时需要继续查看截图，才能核对单靠文字无法判断的部分。

去重也有相同取舍。高度相近的 OCR 内容可以减少重复输入，但短小的状态变化可能恰好决定任务是否完成。设计去重条件时，要看被删掉的部分是否只是重复，还是包含了新的执行结果。

我因此会把事件、OCR 和截图看作互补证据。任何单一来源缺失，都可能改变能够得出的结论。最终摘要需要体现实际材料覆盖到哪里。

### 活动片段为什么先在本地组织

如果每个事件都立即交给语言模型，模型会频繁处理缺少上下文的碎片，同时增加调用次数。先在本地记录和分段，能够把一个相对完整的过程组织好，再决定是否分析。

当前分析器处理已经结束的待分析片段，并先检查持续时间、事件数和截图数。相邻片段还可以根据间隔与应用交集继续合并。这些规则先控制材料规模，再把值得分析的部分交给模型。

应用有交集只是一个近似信号。同一个编辑器里可能切换两个项目，同一个浏览器里也可能先工作再阅读其他内容。合并以后，模型还需要依据具体标题、文字和对象判断主题，必要时保留无法确定的部分。

这条链路把高频采集与较低频分析分开：前者尽量以可控成本保存现场，后者使用更完整的材料形成解释。模型调用次数和原始记录量因此可以分别调整。

### 活动摘要需要说清做了什么，以及依据在哪里

活动分析读取片段里的事件、OCR、窗口和访问材料，生成标题、描述、主题、实体与高亮。内容要具体到实际出现的项目、问题或文档，来源里缺少的信息就保持未知。

例如画面只出现某个仓库和一段报错，可以支持“在排查该仓库的构建错误”；如果没有成功回执，就还缺少“已经修复并发布”的证据。活动理解同样需要区分正在做、尝试过和已完成。

非常短、信息量很低的片段可以跳过分析。更完整的片段也可能只是在随意浏览。先判断这段活动是否值得形成工作记录，再生成摘要，可以减少无意义内容和模型消耗。

日级工作摘要进一步汇集这些片段，让“上午做了什么、后来切换到哪里”成为可读的连续记录。具体依据仍然保留在相应活动材料里。

### 活动总结怎样避免把观察写成结果

浏览器打开某个 PR，只能证明出现过这段访问；看到 diff，可以支持“阅读或检查改动”；出现明确的合并结果，才进一步支持“完成合并”。同一个对象出现于不同画面时，能够说明的动作不同。

分析提示因此要求实体出现在实际材料里，项目无法归属时保持未知，并对低信息量、随意浏览的片段保持克制。具体名称、编号和链接都需要从输入中获得依据。

对我来说，可靠的工作摘要需要兼顾具体程度与证据。只写“处理项目问题”难以检索；补出材料里没有的编号、结果和原因，又会形成虚假的工作记录。能够明确支持的内容写具体，缺少依据的部分保留不确定状态。

日级汇总还要处理片段之间的关系。几个片段围绕同一问题发生，可以按时间组织进展；中间某段材料缺失，就还不能推断完整因果。汇总的可读性来自组织已有证据，而非补齐所有空白。

### 从活动到长期事实，再做一次更严格的筛选

“看了二十分钟某个 PR”有时间线价值。“项目决定长期使用某种部署方式”才可能有跨会话价值。把前者直接塞进事实库，会让每次普通浏览都变成持久背景。

因此，活动分析可以形成工作摘要，同时单独返回长期记忆候选。大多数片段的候选应当为空；少量候选需要说明为什么值得长期保留，再通过写入去重进入事实库。

候选保存活动片段 ID、项目标签等来源信息。以后读到这条事实，可以继续回到产生它的那段活动，检查结论是否被画面和文字支持。

活动来源还意味着另一种成本。截图体积大，OCR 可能涉及私人内容，模型分析可能使用配置的远端服务；本地 OCR 只覆盖文字提取这一环节。保存策略与分析策略需要分别考虑。

当前活动存储按热、温、冷分层维护保留窗口。设计这层时，我关注的是证据在近期查询中仍然可用，以及长期保留哪些摘要更划算。摘要的体积小，但原始截图清理之后，一部分细节也就失去了核对条件。

### 保存窗口怎样影响以后能回答的问题

当前截图分层按拍摄时间计算年龄：默认超过 1 天进入温层，超过 7 天进入冷层，超过 30 天清理冷层截图。层级迁移可以伴随重新压缩，另外还有总存储量触发的清理。

这些门槛表达对近期原始证据的保留优先级。刚发生的工作更可能需要查看画面细节，较久以前的工作通常先从文本与摘要查起。因此，原始截图可以随年龄降低保存成本。

年龄之外还需要总量限制。高频活动可能在保留窗口内产生很多截图，仅按日期清理仍然会占满磁盘。当前流程超过总量上限时，还会按时间清理较旧记录，直到达到目标体积。日期窗口因此也受到实际存储规模影响。

查询时要知道哪些证据仍然存在。旧摘要能够说明曾经记录过某项工作，截图已经清理时，部分画面细节便无法继续核对。保留策略直接决定未来问题能够回答到什么精度。

我会分别观察截图体积、OCR 输入量、待分析片段数与模型消耗。如果存储主要增长在重复画面，应该先调整采样与去重；如果分析队列积压，则要看片段划分、调用成本和处理节奏。它们对应不同的成本来源。

Activity 扩展了记忆的来源，也提高了误判与保存成本。它的价值要通过具体查询体现：能否找到那天的工作片段，摘要能否对应到证据，值得长期保留的信息是否足够克制。

从活动提取长期记忆时，我还会用一个更长的时间尺度检查候选：半年以后，离开这一天的时间线，它是否仍然值得被单独读取。项目持续约束、明确反馈和反复使用的参考入口可能满足这个条件；一次浏览与一次故障处理通常已经由活动记录承接。

这个筛选把信息留在适合的层里。活动层保持时间线的可查性，事实层保留少量能够跨情境复用的内容。两层都有价值，进入长期事实库需要额外的持续使用理由。

## 最后，用完整任务检查这些层是否真的配合起来

每层单独能运行以后，还要看信息穿过几层之后是否保持原意。一个偏好可能经过聊天提取、去重、Sleep 合成和自动召回；一个项目状态可能同时出现在文件、Crystal 和活动摘要里。

我会把原始输入、保存结果、召回结果和最后回答放在一起检查。这样才能区分提取时丢了范围、检索时漏了条目，还是回答阶段误用了正确背景。

| 检查场景 | 观察整条链路里的什么 |
| --- | --- |
| 新会话继续一个项目 | 项目背景能否定位相关会话，工作摘要能否恢复正确的下一步 |
| 同一偏好换种说法出现 | 新写入是否冗余，Top-K 是否被同义条目占满 |
| 两个项目使用不同技术栈 | 提取、合成与召回后，项目范围是否仍然明确 |
| 用户纠正旧偏好 | 旧状态怎样退出，新状态是否真正影响后续回答 |
| 旧对话晚些时候导入 | 相对日期是否按原消息时间解释，计划与完成是否分开 |
| Sleep 中途出现写入失败 | 活动条目、归档与合成结果各处于什么状态，能否恢复 |
| Crystal 关联到相近话题 | 新材料是否属于同一对象，字段有没有来源或冲突 |
| 查询一天的工作过程 | 活动摘要能否回到具体片段，长期事实是否混入普通浏览记录 |

参数评估也使用固定样本。固定事实快照和问题集合，每次只改变查询改写、embedding 模型、门槛或 Top-K 中的一项，比较结果变化以及额外延迟。存储条数、召回条数和模型 token 都有用，最终还要看它们怎样影响任务。

### 用中间结果定位错误发生在哪一步

一次回答用错背景，原因可能发生在很早以前。原始消息本来只针对个人项目，提取结果丢掉范围；事实保存正确，索引没有同步；召回候选正确，装配时缺少时间；模型看到完整背景，仍然沿用了旧状态。

这些错误的修复位置不同。因此，我会把评估拆成可对照的材料：原始输入、提取候选、实际保存条目、检索结果、注入内容与最后回答。沿链路对照，才能决定应该改提示、数据结构、索引维护还是上下文组织。

例如检索没有找到一条已保存事实，先检查它是否有正确向量、是否被范围过滤、是否超过门槛，再看查询改写是否改变了目标。直接放宽门槛，可能只掩盖索引缺失或范围顺序的问题。

合成遗漏条件时，也需要回到整理前后的具体内容。若原事实有条件、候选输入也保留条件，最终合成丢失，就应该检查合成规则与样本；若条件在提取时已经消失，后台整理无法从现有条目里自动恢复它。

### 分开衡量漏掉信息与引入错误背景

需要背景的任务里，漏召回会增加重复解释或误判的机会；不需要历史的任务里，多余召回则可能把过去的局部要求带进来。因此，相关问题和无关问题都要进入查询集。

我会检查结果中有多少条实际相关、应当出现的关键背景有没有出现，以及同一事实是否占用了多个名额。下一步再看模型是否正确使用这些材料：有用的信息可能被忽略，弱相关信息也可能被过度推广。

这里还要保留一组用户更新过的信息。只测静态事实，无法发现新旧状态同时命中、旧向量仍在使用或跨层内容漂移的问题。持续运行的记忆系统，评估样本也需要覆盖变化过程。

对于工作记忆，则使用恢复后的任务行为：能否接着正确的下一步做、是否重新执行已经完成的动作、是否遵守压缩前的约束。摘要写得流畅，只是表达层面的结果；恢复后的动作才说明信息是否够用。

### 按发生频率衡量成本

回答前的查询时延会被用户直接感受到，固定文件的输入成本会在每次加载时累积，回合后提取随交互次数增加，Sleep 则随全库规模增长。它们适合使用不同的观察周期。

我会分别记录查询改写与向量化的等待、单次注入长度、提取候选和实际新增数量，以及每轮维护的扫描量与模型消耗。只有拆到这些环节，才能判断优化应该放在哪里。

例如长期备忘增长后，总输入量不断上升，继续优化向量扫描无法减少这部分成本；相似簇过大导致模型批次增加，则要回到事实粒度和候选生成。成本跟随信息经过的路径，优化也需要回到具体路径。

这套设计还会随实际使用调整。一个新增的记忆形态，应该能解决已有入口难以完成的读取问题；一条新增的维护规则，应该能给出明确条件、检查结果和失败状态。我会用这些要求继续约束系统的增长，让保存下来的信息在未来仍然能被准确使用。
